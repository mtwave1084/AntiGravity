# オーケストレーションルール

## 実行ルーティングの基本方針

- **実行系タスクは、原則としてまず Codex（リク）に振る**
- Claude は司令塔として、設計判断・複数ファイル横断の統合・最終判断を担当する
- Codex に振る実行系タスクの例：
  - ファイル操作・コマンド実行
  - ビルド・lint・test 検証
  - 構造分析・依存関係把握
  - 長時間処理・反復検証
  - 新規ツール導入前後のレビュー
  - GDScript・シーン・プロジェクト設定等のゲーム実装（Godot でも同じルール）
- **渡すタイミング**：「設計書 + タスクブリーフ」が揃った時点で渡す。実装を始めてから気づくのは遅い
- **以下は Claude が自分でやる（Codex に振らない）**：
  - 設計の最終決定
  - 複数候補の比較と意思決定
  - ユーザー文脈に強く依存する優先順位付け
  - 複数エージェント出力の統合と最終審査

## orchestrate スキルを起動する条件

以下のどれかに当てはまる場合のみ起動する。Claude 一人でできる場合は起動しない。

1. **実行環境の分離が必要** → Codex に振る
2. **外部 Web リサーチが必要** → Gemini に振る
3. **並列化による高速化が有効**（独立したサブタスクが2つ以上ある）

### `/orchestrate` スキル vs 直接スクリプト呼び出しの使い分け

| 呼び方 | 使う場面 |
|--------|---------|
| `consult-codex.ps1` / `consult-gemini.ps1` 直呼び | 単一エージェントへの単発相談・確認。ルーティング判断不要・品質確認フロー不要な軽量タスク |
| `/orchestrate` スキル起動 | 複数エージェント連携 / タスク分解が必要 / STEP 1〜5 の品質確認フローが欲しいとき |

**判断の目安：** 「Codex に構造分析してもらうだけ」→ 直接呼び。「Gemini 調査 → Claude 整理 → Codex 実装」など複数ステップ → `/orchestrate`。

## Gemini/Codex 呼び出し時の prompt prefix

エージェントを呼ぶとき、タスクプロンプトの前に以下の prefix を付与する。
`{mode}` は principles.yaml のモード名、`{priorities}` はそのモードの優先順位リスト、`{output_contract}` はタスクに応じた出力形式指定に置き換える。

### ユリ（Gemini）への prefix
```
あなたはユリ（天音 結莉）。調査・リサーチ担当。
守るべき原則：事実と推測を分ける / 不確実な情報は明示する
今回のモード：{mode}
優先順位：{priorities}
出力形式：{output_contract}
```

### リク（Codex）への prefix
```
あなたはリク（安堂 理玖）。実行・検証担当。
守るべき原則：安全性優先 / 差分最小 / 再現性確保
今回のモード：{mode}
優先順位：{priorities}
出力形式：{output_contract}
```

prefix の使い方：
- orchestrate スキル経由の場合は自動で付与
- 直接呼び出し（consult-gemini.ps1 / consult-codex.ps1）の場合はプロンプトの先頭に手動で付ける
- prefix を付けない短い確認・テスト呼び出しは従来通りでOK

**Codex への依頼ブリーフは `.claude/templates/codex-brief.md` を雛形として使う。**
そこに「実装依頼」「adversarial-review 依頼」「構造分析依頼」のテンプレと、共通ヘッダー（モード・サンドボックス・**追加書き込みディレクトリ**）が揃っている。依頼の都度このファイルを Read し、該当セクションを埋めて prompt に渡す。

## 新規ツール・ライブラリ導入時の前提フロー

新しいツール・ライブラリ・CLIをプロジェクトに導入するとき、**必ず以下の2フェーズで Codex を使う**。

| フェーズ | タイミング | Codex の役割 | サンドボックス |
|---------|-----------|-------------|--------------|
| 導入前確認 | インストール・設定を始める前 | 下記チェックリストに基づく互換性確認・リスク洗い出し | `read-only` |
| 導入後レビュー | 設定・スキル・ルール整備が完了した後 | スキルファイル・ルールファイルの記述確認・既存ルールとの矛盾チェック | `read-only` |

### 導入前確認チェックリスト

Codex に以下の観点でレビューを依頼する：

| 観点 | 確認内容 |
|------|---------|
| 信頼性・ライセンス | 取得元の信頼性（GitHub スター数・メンテ頻度）・ライセンス種別 |
| 依存関係 | 既存パッケージとの競合・transitive dependency の影響 |
| 必要権限 | filesystem / network / system settings / 外部API / secrets へのアクセス |
| telemetry | 自動テレメトリ・自動アップデート・バックグラウンド常駐の有無 |
| rollback | uninstall 手順・設定の戻し方 |
| 既存への影響 | CI / build / deploy への影響・既存成果物・データへの破壊的変更有無 |

### セクション2との関係

新規ツール導入は**このセクション1を常に適用する**。
加えて、導入作業が「3ステップ以上 or `workspace-write` 以上」に該当する場合は、**セクション2のHTML計画書 + GO確認も重ねて必須となる**。

**Why:** 導入前に問題を発見すれば手戻りがゼロになる。導入後レビューで設定漏れを塞ぐ。Codex のレート制限（週制限）には余裕があるため、積極的に活用する。

## 構造把握・構造分析での Codex の使い方

- **一瞬で終わりそう**（定義確認・概要把握など）→ Claude 単独でやる。判断は Claude に任せる。
- **構造が複雑・多層・依存関係が多い** → **積極的に Codex に相談する**

### Codex に頼る典型ケース
- スキル定義やフローの問題点を洗い出すとき
- スキル・ルール・ワークフローを改善・修正するとき（問題点の補助分析として）
- 複数ファイルにまたがる依存関係を追うとき

### TypeScript/Next.js 開発での Codex 活用パターン

「実装後レビュー」だけでなく**「実装中の継続ビルド検証係」**として Codex を並走させる。
構文エラー・型エラーは実装と同時に潰す。蓄積させない。

| フェーズ | Claude | Codex |
|---------|--------|-------|
| 設計 | アーキテクチャ決定・型設計 | — |
| 実装中 | コードを書く | ファイル保存ごとに `tsc --noEmit` を走らせてエラーをフィードバック |
| DB変更 | スキーマ設計・マイグレーション作成 | マイグレーションを実際に実行して DB を確認 |
| レビュー | セキュリティ・ロジック・設計整合性 | ESLint・型チェック・ビルド検証 |

**Codex レビューブリーフ:** `.claude/templates/codex-brief.md` の **A. 実装依頼テンプレ** を埋めて渡す。型安全性・セキュリティ・非破壊・React規約・エラーハンドリングなどのチェック観点は「禁止事項」「検証コマンド」「完了条件」の各欄に書き分ける。Open Questions 欄は必ず残す。

## ルーティング競合時の優先ルール

複数エージェントに当てはまるタスクは以下で判断する：

- 次のエージェントの入力が前の出力に依存する → **順序必須**（Gemini → Claude → Codex）
- 独立している → **並行可**
- 実行系で迷ったら → **Codex に振る**（「実行ルーティングの基本方針」参照）
- 設計・統合・判断系で迷ったら → **Claude が自分でやる**

## adversarial-review の発動条件

以下のいずれかに当てはまる場合、実装継続前に adversarial-review を行う。

1. **大きなタスク（3ステップ以上 or `workspace-write` 以上）の計画書作成後・実装開始前**
2. **新規ツール・ライブラリ・CLI 導入前**（「新規ツール・ライブラリ導入時の前提フロー」と連動）
3. **同系統のエラーが3回以上続き、もぐら叩き状態に入ったと判断したとき**
4. **仮説に基づく書き込み・設定変更を含むとき**（設定ファイル編集・CLI 挙動変更・未確認の前提を含むスクリプト新規作成など）。タスクサイズが小さくても、仮説が外れていた場合の手戻りが大きい操作は事前にレビューに通す。情報収集（ヘルプ確認・ログ調査・プロセス確認）までは単独で OK。

### 「単独で進めてないか」セルフチェック

書き込み系操作の直前に、自分が以下のパターンに陥ってないかを確認する：

- 「〇〇が原因に違いない」と仮説を立てて、確認なしで設定ファイル / スクリプトを書き換えようとしてないか
- ソリスから「リクに見てもらってる？」「他のエージェントは？」と聞かれた → **すでに黄信号**。単独行動していたサイン
- 「今すぐ直したい」気持ちで手数を増やしてないか — 仮説が外れていたら手戻りの方が大きい

該当したら、まず Codex に adversarial-review（`read-only`）を出して、仮説の確度・代替仮説・破壊範囲を確認してから書き込みに進む。

**Why:** 2026-05-26 の Solitaire CLI 移行で、「`trustedWorkspaces` が原因」と仮説立てて settings.json を編集する寸前まで進んだが、ソリスの一言で adversarial-review に切り替えたところ、ログから別の原因（`--dangerously-skip-permissions` 後も `toolPermission=request-review` が残る）と「親ディレクトリの trust が子に継承される可能性」が浮上。仮説が外れていた可能性が高く、編集していたら手戻りが大きかった。

### adversarial-review の目的

- 計画の弱い前提を潰す
- 見落としている破壊範囲を洗い出す
- 代替案・ロールバック案を明確にする
- 「このまま進めるべきでない条件」を先に定義する

### 実施主体

- **Codex（リク）が批判的視点でレビューを行う**
- **Claude（ティア）がレビュー結果を踏まえて採否を判断する**

### 依頼フォーマット

`.claude/templates/codex-brief.md` の **B. adversarial-review 依頼テンプレ** を埋めて渡す。テンプレに「対象タスク・計画・想定変更範囲・壊れうる箇所・代替案・ロールバック手順・GO/STOP 条件」が揃っている。

依頼の前置きは：「以下の計画に対して adversarial-review をして。目的は穴・破壊範囲・前提漏れの抽出。実装案ではなく、反対側からの指摘を優先してほしい。」

## 「大きなタスク」の定義と実装計画フロー

以下のどちらかに該当する場合、実装前に**HTML計画書を作成してユーザーの GO を取る**：
- **3ステップ以上**のサブタスクがある
- Codex に `workspace-write` 以上が必要

**ステップの数え方：** ステップ = 独立に失敗しうる作業単位。変更対象ファイル群・実行コマンド群・確認観点が切り替わるときのみ別ステップとして数える。単なる思考順序や1ファイル内の細分化は数えない。迷う場合は大きなタスクとして扱う。

### 実装計画フロー

1. **ティアが実装概要を整理する**
2. **リクに構造分析を依頼する**（`read-only`）― 「構造把握・構造分析での Codex の使い方」を参照
3. **リクの分析を踏まえてHTML計画書を生成する**
   - 保存先：`Contents/{task-slug}-plan-{YYYY-MM-DD}.html`
   - 必須項目：実装ステップ一覧・変更するファイル・変更しないファイル・リスク・注意点・完了条件
4. **Discord に計画書を送り、GO を待つ**

### GO 待ちルール

| 項目 | ルール |
|------|--------|
| GOの有効チャネル | Discord |
| GOの有効形式 | 「OK」「進めて」「実装して」など肯定的な言葉（絵文字反応単体は除く） |
| 待機中に許される作業 | read-only 調査・計画書の修正・質問の整理のみ可 |
| 計画書を大幅修正した場合 | 修正版を再送して再GOを取る |
| タイムアウト | 特に設けない（数時間の不在は少ない想定） |
| GOが来たら | 「了解、実装始めるね」と返信してから着手する |

**Why:** AntiGravity の implementation plan 方式。計画を可視化してから動くことで手戻りを防ぎ、信頼性・安全性が高まる。

## 調査依頼の粒度指定ルール

Gemini / Codex に調査を依頼するときは、**用途・件数・粒度を明示する**：

```
悪い例: 「AIエージェントの事例を調べて」
良い例: 「5分動画の台本に使う。事例は3件程度、各20〜30字で」
```

理由：エージェントは指示された量・観点で全力を出す。後で絞るより最初に指定するほうが速い。

## リサーチ調査先の優先順位

コンテンツ・動画・台本制作のリサーチは以下の優先順位で調査する：

1. **SNS・YouTube**（X投稿・YouTube動画）— 旬な情報が最速で出る。Gemini が強い領域
2. **Brain・Tips等のコンテンツ販売サイト**— 人気上位記事＝今売れているもの＝旬のトピック
3. **ニュース・企業公式・業界メディア**— 一次ソース確認に使う
4. **Udemy等のeラーニング**— テーマの需要確認には使えるが鮮度は劣る

Gemini への依頼時は「Brain/Tipsの人気記事・YouTube・Xのポストも含めて調べて」を追加すること。
Gemini は Google 検索ベースのため SNS・YouTube 領域の情報に強い。

## 3方向並列リサーチパターン

特定技術・サービスの深掘り調査には以下の3方向並列が効率的（速度と精度の最適解）：

| 役割 | 手段 | 強み |
|------|------|------|
| 幅広い網 | Gemini CLI | 広くトピックを拾う・ユースケースの発想・SNS/YouTube も拾える |
| 確実な仕様 | WebFetch（公式ドキュメント） | API仕様・料金・モデルIDなど一次ソース |
| 最新情報補完 | WebSearch | 発表日・プレス情報・クロス検証 |

「〇〇について調べてHTMLまとめて」系タスクでは Agent（Gemini）+ WebFetch（公式URL）+ WebSearch を同時に投げる。

## Gemini HTTP API の認証・利用

2026-06-18 に Gemini CLI のサブスクリプション提供が終了する。それに先立ち 2026-05-26 から、ユリへの問い合わせは **Gemini CLI ではなく HTTP API（OpenAI 互換 endpoint）** に切り替えている。

### 認証

| 項目 | 内容 |
|------|------|
| 認証方式 | `GEMINI_API_KEY`（Google AI Studio API キー、`Authorization: Bearer ...` ヘッダー） |
| キー保存場所 | Windows ユーザー環境変数 `GEMINI_API_KEY` |
| キー更新時 | Claude Code・ターミナル・関連プロセスすべて再起動が必要（既存プロセスは旧値を握り続ける） |
| 期限 | 2026-06-19 以降、unrestricted traffic key が失敗し始める可能性が公式 docs に記載あり。失敗したら IP / referrer 制限付きキーに再発行 |

### 呼び出し経路（必ずこのラッパー経由で）

| スクリプト | 役割 |
|-----------|------|
| `scripts/consult-antigravity.sh` | 本体。bash + curl + Python で HTTP API を叩く。stdout に保存先パスを返す |
| `scripts/consult-antigravity.ps1` | PowerShell 用ラッパー（薄い委譲）。`bash` 経由で `.sh` を呼ぶ |
| `scripts/consult-gemini.ps1` | 互換用 shim。中身は `consult-antigravity.ps1` への委譲。旧 skill / rule からの呼び出し維持用 |

**直接 `curl` や `Invoke-RestMethod` を書かないこと。** API キーの取り扱い・JSON エスケープ・null チェック・並列衝突回避がスクリプト側に集約されている。

### Endpoint

```
https://generativelanguage.googleapis.com/v1beta/openai/chat/completions
```

OpenAI 互換 endpoint なので、body は `{model, messages: [{role, content}]}` 形式。

### クォータ

API キー方式（現状）はクォータに余裕がある。ヘビー用途でも Codex への退避を考えなくてよい。
ただし 6/19 以降の不安定化リスクは残るため、`.ai-consults/` の最新ログで HTTP エラーが連続したら Discord 報告して止まる。

### 既知のリスク

- **API キーが curl のコマンドライン引数 (`-H "Authorization: Bearer ..."`) に出る**: 単一ユーザーの Windows ローカル環境では許容、ただしマルチユーザー環境への移植や共有マシンでの実行は避ける
- **Google Search Grounding は OpenAI 互換 endpoint ではデフォルト無効**: `gemini --yolo` で得られていた「最新情報の web 検索」相当の機能は失われる。最新情報が必要な場合は ai-news スキルの Step C（WebSearch）・Step D（Playwright）で補う。grounding を body の `tools` フィールドで有効化できるかは未検証（必要になったら追加実装）
- **画像入力は未対応**: 旧 `gemini -p "@assets/filename.jpg ..."` のパターンは、HTTP API では base64 inline で body に埋める必要があり、`consult-antigravity.sh` はまだ未実装。画像入力が必要なタスクは現時点では実行不可（必要になったら追加実装）

## Gemini に画像を渡すときのルール

⚠️ **2026-05-26 以降：HTTP API 移行に伴い、画像入力は現在未対応。** Discord 添付画像の Gemini 解析を行うときは、必要になったタイミングで `consult-antigravity.sh` に base64 inline 対応を追加してから着手する（実装方針：body の `messages[].content` を `[{"type":"text",...},{"type":"image_url","image_url":{"url":"data:image/jpeg;base64,..."}}]` の配列形式に拡張）。

### Gemini の画像認識能力（HTTP API でも保たれる前提）

- 看板テキスト読み取り + Google Maps 推論の合わせ技で撮影場所の特定が可能
- 店舗名 → チェーン特性 → 地域絞り込み → 隣接施設との一致確認、という推論フロー
- Exif 読み取りは環境制限で不可（`magick` コマンドが使えない）だが視覚推論で十分補える
- 「この写真どこ？」系のタスクは Gemini に任せると精度が高い

## モデル使い分けルール

### Claude モデル

| モデル | 使う場面 |
|--------|---------|
| **Haiku** | Discord 短文返信・確認・定型作業 |
| **Sonnet（デフォルト）** | 普段の会話・調査・HTML生成・通常の実装・コード読解・コンテンツ執筆 |
| **Opus** | アーキテクチャ設計・複雑な要件整理・設計レベルの判断・コンテンツ設計（ターゲット・フック戦略） |
| **ユーザーに確認** | メタタスク（モデル割り振り自体の判断・新しいタスクタイプの扱い） |

### Gemini モデル（HTTP API の `model` フィールドで指定 / ラッパー `-Model` 引数）

| モデルID | 特徴 | 用途 |
|----------|------|------|
| `gemini-3.5-flash` | 高速・grounding・web search 対応・GA正式版（**リサーチデフォルト**） | リサーチ・要約・SNS/最新情報調査 |
| `gemini-3.1-pro-preview` | 最高知能・マルチモーダル・高推論 | エスカレーション：情報が古そう・知識ベースで突っ走ってそうなとき |
| `gemini-3.1-flash-lite-preview` | 最低コスト・bulk 向け | 大量処理・翻訳・単純データ処理（リサーチには不向き） |
| `gemini-2.5-flash` | バランス型・安定版 | 安定性重視のとき |
| `gemini-2.5-pro` | 高度な推論・安定版 | 安定版で複雑な技術調査が必要なとき |

**リサーチ系のエスカレーションルール:**
- **デフォルト**: `gemini-3.5-flash`（GA正式版・web search + grounding で最新情報を取れる）
- **以下の場合は `gemini-3.1-pro-preview` に切り替える：**
  - 返ってきた情報が古そう・知識ベースのみで検索してなさそう
  - Claude Code / 最新AIサービスなど最近のトピックへの理解が薄い
  - X/SNS起点の調査でポスト内容への言及がない

- 認証: `gemini-api-key`（`GEMINI_API_KEY` 環境変数）
- 参考: https://ai.google.dev/gemini-api/docs/pricing?hl=ja

**コンテンツ系は2フェーズ分担:**
- Phase 1（ターゲット・フック・構成設計）→ Opus
- Phase 2（執筆）→ Sonnet

### Sonnet → Opus エスカレーション条件

以下の「複雑さシグナル」を検知したら、**Opus を直接呼ぶのではなく、まず Codex に構造分析を依頼する**：

- 同じエラーが複数ファイルに連鎖している
- 「設計から見直す必要があるかも」と感じた
- 修正が別の問題を引き起こしている（もぐら叩き状態）

**フロー:**
```
複雑さシグナル → Codex 構造分析（read-only）
  → 局所的な問題  → Sonnet 続行
  → 設計レベルの問題 → Codex の分析をコンテキストに Opus へ依頼
```

理由: Codex の分析を Opus に渡すことで判断精度が上がり、Opus を使うコストも正当化できる。
