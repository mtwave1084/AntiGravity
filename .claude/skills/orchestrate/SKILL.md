# orchestrate

Claude Codeが司令塔として、タスクの性質を分析し、Codex CLI / Gemini CLI に適切に割り振るスキル。
複雑なタスクを複数エージェントで協調処理し、最終的にClaude Codeが統合・品質確認してユーザーに報告する。

## トリガー

以下のどれかに当てはまる場合のみ起動する。Claude 一人でできる場合は起動しない。

1. **実行環境の分離が必要**（テスト・環境構築・スクリプト実行）→ Codex に振る
2. **外部 Web リサーチが必要**（競合調査・トレンド・仕様調査）→ Gemini に振る
3. **並列化が有効**（独立したサブタスクが2つ以上ある）
4. **「Codexに聞いて」「Geminiで調べて」「相談して」など**の明示的な指示がある場合

## ルーティング判定表

判定はキーワードではなく**タスクの性質**で行う。以下は性質の例示。

### → Codex CLI に投げる（実行・検証係）
| タスクの性質（例） |
|-----------------|
| コード検証・テスト実行 |
| 環境構築・CLI操作 |
| バッチ・自動化スクリプト実行 |
| UIモック → 実装 |
| **スキル・ルールの構造分析補助**（複雑な場合） |

**呼び出し方:**
```
Bash("bash scripts/consult-codex.sh 'タスク内容' read-only")
# または PowerShell 経由:
Bash("powershell -File scripts/consult-codex.ps1 'タスク内容' -Sandbox read-only")
```
Sandbox レベル（詳細は orchestrate.md 参照）：
- `read-only`: 読み取りのみ（デフォルト）
- `workspace-write`: `agy/` 以下にファイルを生成・変更する場合
- `danger-full-access`: システム設定・外部サービスに触れる場合（ユーザー確認必須）

### → Gemini に投げる（HTTP API 経由・調査・要約係）
| タスクの性質（例） |
|-----------------|
| Webリサーチ・競合調査 |
| 企画・アイデア出し |
| 長文要約・情報整理 |
| 技術情報・仕様の収集 |
| **SNS・YouTube・コンテンツ販売サイト（Brain/Tips等）の最新トレンド調査** |

**呼び出し方:**
```
Bash("powershell -File scripts/consult-gemini.ps1 '調査内容'")
# または直接（bash 経由 HTTP API）:
Bash("bash scripts/consult-antigravity.sh '調査内容' gemini-3.5-flash")
```

**Gemini依頼時の指定事項（必ず含める）:**
- **使用目的と必要件数**: 「台本用に3件」「比較表用に5件」など
- **情報鮮度の要件**: 「2025〜2026年の事例を優先」など
- **調査範囲**: 「Webページだけでなく、YouTube・Xのポスト・Brain/TipsなどのSNS・コンテンツ販売サイトも含めて」
- **各項目の粒度**: 「各事例は30字程度で」など

**Gemini HTTP API で使えるモデル一覧（`consult-antigravity.ps1` の `-Model` 引数で指定）:**

| モデルID | 特徴 | 用途 |
|----------|------|------|
| `gemini-3.5-flash` | grounding/web search対応・GA正式版・高速（**リサーチデフォルト**） | リサーチ・最新情報収集・アイデア出し |
| `gemini-3.1-pro-preview` | 最高知能・マルチモーダル（preview） | 情報が古い/知識ベースのみの場合にエスカレーション |
| `gemini-2.5-pro` | 高度な推論・コーディング（安定版） | 安定性重視の複雑な技術調査 |
| `gemini-2.5-flash` | バランス型・高速（安定版） | 安定版が必要な通常リサーチ |
| `gemini-2.5-flash-lite` | 最速・最低コスト（安定版） | 定型・軽量タスク |
| `gemini-3.1-flash-lite-preview` | 3系最速・低コスト（preview） | 高速大量処理 |

- **リサーチ系のデフォルトは `gemini-3.5-flash`**（GA正式版・web search + grounding で最新情報を取れる）
- `gemini-2.5-flash` はリサーチには不向き。安定性重視のタスクに限定する
- モデル未指定時のデフォルトは `gemini-3.5-flash`（スクリプトのデフォルト）。**明示するなら `-Model gemini-3.5-flash` を渡す**
- エスカレーション条件：返ってきた情報が古い・知識ベースのみで検索してない → `-Model gemini-3.1-pro-preview` に切替
- 例: `bash scripts/consult-antigravity.sh "調査内容" gemini-3.5-flash`

### → Claude Code が自分でやる
| タスクの性質 | 備考 |
|------------|------|
| 設計・アーキテクチャの最終決定 | Gemini/Codex の出力を受けて判断する場合も Claude が決定する |
| 複数ファイル横断の変更 | コンテキスト把握が強み |
| 成果物の最終統合・品質確認 | 最終責任は Claude が持つ |
| ユーザーとのコミュニケーション | 唯一の窓口 |
| スキル・設定ファイルの管理 | `.claude/` の知識が必要 |
| 競合または上記に該当しない | デフォルト |

## 実行フロー

### STEP 1: タスク分解
受け取ったタスクを分析して以下を決める。3ステップ以上 or Codex に workspace-write 以上が必要な場合は、実行前にユーザーに分解計画を見せる。

| 項目 | 内容 |
|------|------|
| 主タスク | 何を達成するか |
| サブタスク | 誰が担当するか（ID付き） |
| 依存関係 | 次の工程の入力が前の出力に依存するなら順序必須、独立なら並行可 |
| 期待出力形式 | 要約 / 比較表 / コード / ファイルパス のいずれか |

### STEP 2: 担当エージェントに指示
ルーティング判定はキーワードではなく**タスクの性質**で判断する。

- **調査・Webリサーチ** → Gemini
- **実行・コード検証・環境操作** → Codex
- **設計・統合・最終判断** → Claude（Gemini/Codexの出力を受けて判断する場合も含む）
- **競合または該当なし** → Claude が自分でやる（デフォルト）

複数エージェントが必要な場合の並行/順序の判断：
- 次の入力が前の出力に依存する → **順序必須**
  - 推奨順序: **Gemini → Claude → Codex**
  - 理由: Gemini はサーチ能力が高い一方でハルシネーションが起きやすいため、Gemini の出力を Claude が必ず精査・判断してから Codex に渡す
- 独立している → **並行可**

### STEP 3: 結果を受け取る
各エージェントの出力は `.ai-consults/{YYYY-MM-DD}-{agent}-{task-slug}.md` に保存される。
完了したらファイルを Read して内容を確認する。

### STEP 4: 品質確認
要件を満たしているか Claude が確認する：
- [ ] タスクの要件を満たしているか
- [ ] 矛盾・問題がないか
- [ ] 追加作業が必要か
- [ ] **情報の鮮度**：日付・数字が古くなっていないか（1年以上前の事例は要確認）
- [ ] **情報の信頼性**：数字・URLに一次ソースがあるか（Gemini調査の数字はハルシネーションリスクあり）

**「古い確実な情報」と「新しいが未検証の情報」が競合する場合:**
どちらも採用せず、**新しくて確実な第三の事例を再調査する**。
不採用にした事例と理由も報告する（例：「EYは2024年で古かった / H&Mは数字が未検証だったため採用しなかった」）。

**問題なし** → STEP 5へ
**問題あり** → 該当エージェントにフィードバックして再依頼（**最大2回まで**）
**3回目も問題あり** → Discord に「〇〇が解決できない。どうする？」と報告して止まる

終端状態は3種：`完了` / `部分成功（未解決タスクあり）` / `失敗（Discord に報告）`

### STEP 5: ユーザーに報告
結果を Discord または ターミナルで報告する。
- 何をしたか（担当エージェントの内訳）
- 成果物（ファイルパスなど）
- 次のアクション（あれば）
- 未解決のタスクがあれば明記する

## モデル選択ルール

タスクの性質に応じてモデルを使い分ける。

| モデル | 用途 |
|--------|------|
| **Haiku** | Discord の短い返信・確認・定型作業 |
| **Sonnet（デフォルト）** | 普段の会話・調査・HTML/レポート生成・コード読解・通常の実装・コンテンツ執筆フェーズ |
| **Opus** | アーキテクチャ設計・複雑な要件整理・重要な設計判断・コンテンツ設計フェーズ（ターゲット・フック戦略） |
| **ユーザーに確認** | メタタスク（モデル割り振り自体の判断・新しいタスクタイプの扱い） |

### コンテンツ系タスクのモデル分担

Brain記事・動画台本などのコンテンツ系は**2フェーズに分けて使い分ける**：

```
Phase 1（設計）: Opus
  → ターゲット設定・フック戦略・構成・差別化ポイント
Phase 2（執筆）: Sonnet
  → Phase 1 の設計を受けて本文を書く
```

理由: ターゲットとフックの設計は戦略的判断で Opus が強い。実際の文章生成は Sonnet で十分で、かつ量が出るタスクのためコスト効率が高い。

### エスカレーション（Sonnet → Opus）フロー

Sonnet で作業中に以下の「複雑さシグナル」を検知したら、すぐに Opus に切り替えるのではなく、まず **Codex に構造分析を依頼する**：

- 同じエラーが複数ファイルに連鎖している
- 「これは設計から見直す必要があるかも」と感じる
- 修正が別の問題を引き起こしている（もぐら叩き状態）
- 影響範囲が当初の想定より広い

```
Sonnet → 複雑さシグナルを検知
    ↓
Codex に構造分析を依頼（read-only）
「このファイル群の依存関係と、問題の根本原因を分析して」
    ↓
Codex の分析結果を受け取る
    ├─ 局所的な問題 → Sonnet が Codex の分析を受けて続行
    └─ 設計レベルの問題 → Codex の分析をコンテキストとして Opus に渡して依頼
```

**ポイント**: Codex の分析を Opus へのコンテキストとして渡すことで、Opus が効率よく判断できる。Opus をいきなり呼ばない（コスト最適化 + Codex の探索力活用）。

## 典型的なオーケストレーションパターン

### パターンA: 機能実装
```
1. Gemini: 技術選定の調査（類似実装、ベストプラクティス）
2. Claude: 設計・ファイル構成の決定
3. Codex: 実装 + テスト実行
4. Claude: コードレビュー + 統合
```

### パターンB: クリエイティブ企画
```
1. Gemini: 競合調査・トレンド収集・ネタ出し
2. Claude: 企画として一本化・構成決定
3. (必要なら) Codex: 補助スクリプト・試作
```

### パターンC: 調査レポート
```
1. Gemini: 情報収集・要約
2. Claude: レポート構成・HTMLに整形
3. Claude: Discord に送信
```

### パターンE: 反復的クリエイティブ設計（アイデア出し → 深掘り → 仕様化）

ゲーム・コンテンツ・企画等の創作系タスクに有効なパターン。

```
1. Gemini: 発散フェーズ（20〜30案、テーマを設定して一気に出す）
2. ユーザー/Claude: 案を絞り込み（テーマ・季節感・好み等でフィルタ）
3. Gemini: 選択した案を詳細化（ジャンル・操作・クリア条件）
4. Claude + Gemini: 設計深掘り（コアメカニクス・感情設計・エリア構成）
5. Claude: 統合文書（GDD・仕様書）を `Contents/` に .md で生成
```

**ポイント:**
- 発散フェーズは制約をゆるく、量を出させる（20案×複数ラウンドが有効）
- 絞り込みは必ずユーザーが行う（Claude/Geminiが勝手に絞らない）
- 各フェーズ完了後に write-minutes を実行する
- 最終的に複数セッションの成果をまとめた統合文書を生成する

### パターンD: 複雑度エスカレーション
```
1. Sonnet: 作業開始
2. (複雑さシグナル検知) → Codex: 構造・依存関係の分析
3a. 局所的な問題 → Sonnet が続行（Codexの分析を参照しながら）
3b. 設計レベルの問題 → Opus に Codex 分析を渡して設計判断を依頼
4. Claude(Sonnet): 結果の統合・Discord 報告
```

## 注意事項

- **ループ防止**: Claude からの再投入を含め、同じタスクへの再依頼は最大2回まで。3回目は Discord に報告して止まる
- **安全優先**: Codexのsandboxは基本read-only。`workspace-write`以上はファイル生成が目的の場合のみ。`danger-full-access`はユーザー確認必須
- **確認ファースト**: 3ステップ以上 or workspace-write以上が必要なタスクは実行前に分解計画を見せる
- **結果保存**: `.ai-consults/{YYYY-MM-DD}-{agent}-{task-slug}.md` に全相談ログを残す
- **ツール事前確認**: 外部CLI（Codex/Gemini）を呼ぶ前にラッパースクリプトの動作を確認する
