HIGH Claude + Codex ① 再試行ループに停止条件がない

STEP 4「問題あり → 再依頼」に上限回数・打ち切り条件・エスカレーション先がない。品質基準を満たせない場合、同じエージェントへの再依頼が無限に繰り返される。

Codex 補足
注意事項の「Codex/Gemini に振った後、さらに再委譲しない」は下位エージェントからの再委譲を禁じているだけで、Claude が同一タスクを再投入するループは防いでいない。統制対象がずれている。

→ 改善案

STEP 4 に以下を追記する：
• 再依頼は最大2回まで
• 3回目も問題あり → Discord に報告して止まる（CLAUDE.md の「同じエラーが3回で止まる」ルールに合わせる）
注意事項のループ防止文を「Claude からの再投入も含む」に修正する
HIGH Claude ② トリガー条件が曖昧すぎる

「複数ステップにわたる複雑なタスク」「明らかに専門作業が含まれる」はほぼあらゆるタスクに当てはまり、Claude が自分でやるべき場面との境界がない。意図しない orchestrate 起動が頻発する。

→ 改善案

「Codex/Gemini を呼ぶ明確な理由（①実行環境の分離が必要、②外部Webリサーチが必要、③並列化による高速化が有効）のどれかに当てはまる場合のみ起動」と否定条件も合わせて明記する。
HIGH Codex ③ ルーティング競合時の優先ルールがない

ルーティング判定表は Codex / Gemini / Claude 自身の三択に見えるが、優先順位と競合解決ルールがない。「技術情報の収集を含む実装タスク」のように Gemini と Codex の両方に該当するケースで判断が止まる。

Codex 補足
典型パターン（A/B/C）は例示として有用だが、「いずれのパターンにも当てはまらない場合のデフォルト分岐」が未定義。

→ 改善案

競合解決ルールを追記する：
• 調査結果が実装の入力になる → 順序必須（Gemini → Codex）
• 独立したタスク → 並行
• どちらにも当てはまらない → Claude が自身で判断し実施
「デフォルト: Claude が自分でやる」を明記する

🟡 中優先度

MID Codex ④ 途中失敗時の戻り先・終端状態が未定義

STEP 2 でタスクを振り出した後、失敗した場合に STEP 1 へ戻るのか STEP 2 で再ルーティングするのかが不明。また STEP 5 は「完了」しか想定しておらず、「部分成功」「一部失敗」「保留」の終端状態がない。

→ 改善案

STEP 4 に終端状態を3種追加する：完了 / 部分成功（未解決タスクあり） / 失敗（Discord に報告）。失敗時は STEP 2 で別エージェントへ再ルーティングするか、Claude が自分で実施するかを選択する。
MID Claude + Codex ⑤ Sandbox 昇格条件が未定義

Sandbox の選択肢（read-only / workspace-write / danger-full-access）は列挙されているが、「どの条件で上げるか」「ユーザー承認が必要な境界はどこか」が書かれていない。

→ 改善案

使用条件を明記する：
• read-only → 読み取り・確認のみ（デフォルト）
• workspace-write → agy/ 以下にファイルを生成・変更する場合
• danger-full-access → システム設定・外部サービスに触れる場合（必ずユーザー確認）
MID Codex ⑥ エージェント間の入出力契約が弱い

STEP 1 でタスク分解はするが、どの粒度・形式で次工程へ渡すかが未定義。「Gemini の調査結果」から「Claude の設計」への受け渡しが「要約なのか比較表なのか推奨案なのか」が不明で、毎回暗黙の判断に頼っている。

→ 改善案

STEP 1 の出力フォーマットを定義する：タスクID・担当エージェント・期待する出力形式（要約 / 比較表 / コード / ファイルパス）の3点セットを書く。次工程はこれを受け取る形で接続する。
MID Claude ⑦ 「Claude 自身でやる」条件が Gemini ルートと矛盾

「設計・アーキテクチャ決定は Claude がやる」とある一方、パターンAでは「Gemini 調査 → Claude 設計」の流れ。「設計は Gemini を使わずに全部 Claude がやる」と「Gemini の調査を受けて Claude が決定する」が混在し、読む人によって解釈が変わる。

→ 改善案

「Gemini の調査結果をインプットとして、最終的な設計判断は必ず Claude が行う」と明記し矛盾を解消する。

STEP 3 で「.ai-consults/ のファイルを Read して確認」とあるが、命名規則・タスクIDとの対応がなく、どの出力がどの入力に対する結果か追跡できない。

LOW Claude + Codex ⑨ 「大きなタスク」の定義がない

注意事項に「大きなタスクは確認ファースト」とあるが「大きい」の定義がなく、毎回確認して進行が止まるか、逆に確認なしで進めるかが判断者依存になる。

→ 改善案

「3ステップ以上 or Codex に workspace-write 以上が必要な場合は、実行前にユーザーに分解計画を見せる」を目安として追記する。
LOW Claude ⑩ ルーティングキーワードが日本語専用

ルーティング判定表のキーワードがすべて日本語。英語表記や混在した指示が来るとマッチしない。

→ 改善案

キーワード一致ではなく「タスクの性質（調査 / 実行 / 設計）はどれか」を意味的に判断する記述に切り替える。キーワード表はあくまで例示として残す。

全体の傾向（Claude + Codex 共通見解）
「何をするかは書いてあるが、失敗したらどうするか・何を渡すか・いつ止まるかが抜けている」パターンが一貫して見られる。 高優先度の①〜③を先に修正するだけで、無限ループ・誤ルーティング・競合時の停止という最も実害の大きい問題が解消できる。
