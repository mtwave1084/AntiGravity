9. 無料ガイドと違う理由
9-1. 自己流は事故流
「Claudeの使い方」を教えるガイドは、無料でいくらでもあります。30万字の無料ガイドも、YouTube動画も、山ほどある。

じゃあなぜ、ほとんどの人はClaudeを使いこなせていないのか？

機能の説明を読んでも、「仕組み」は作れないからです。

このガイドが無料の情報と決定的に違う理由が3つあります。

① 設計思想が入っている

なぜCLAUDE.mdをこう書いたのか。なぜこのルール構造にしたのか。「なぜ」の部分は、実際に運用して試行錯誤した人にしか書けない。機能の説明は無料で全部ある。設計の哲学だけが、一次情報にしかない。

② 失敗の記録がある

$100飛ばした事件、ある。CLAUDE.mdに全部詰め込んで後半を無視された事件、ある。無料ガイドは成功事例しか載せない——このガイドは失敗も出す。詰まりやすいポイントを先に知っとけば、同じ壁にはぶつからなくて済む。

30. 設計思想の違い — ここが一番大事


ここが一番大事なポイントです。

Cursor、Antigravity、VS Code——これらは「エディタ」です。ファイルを見たり、コードを書いたりする「作業場」。

Claude Codeは「AIエージェント」です。ターミナルから起動して、実際に仕事をする「作業者」。

つまり、CursorもAntigravityもVS Codeも、「Claude Codeをどこで使うか」の違いでしかない。どのエディタのターミナルからでもClaude Codeは起動できます。

エディタ = 作業場。Claude Code = 作業者。作業場を選ぶのは好みの問題ですが、作業者はClaude Codeが一番良いです。

LP制作、LINE配信設計、競合分析、KPIダッシュボード、議事録構造化——ビジネスの全工程を回せるのはClaude Codeだけ。

31. Claude Code vs Cursor
前提として、CursorもAntigravityも「エディタ（作業場）」です。Claude Codeはどのエディタのターミナルからでも起動できるので、CursorとClaude Codeは競合ではなく「一緒に使える」関係です。

その上で、Cursorは優れたツールです。

31-1. Cursorの強み
速い: レスポンスが速く、コーディング中のテンポが良い

ファイルを勝手に作ってくれる: コードを書く流れの中で、必要なファイルを自動生成してくれる

Cursorは「コードを書く体験」に特化して磨き込まれています。

31-2. Claude Codeの強み
CLAUDE.md（記憶OS）: プロジェクトのルール・判断基準をファイルとして管理できる。セッションをまたいで記憶が引き継がれる

Skills: 繰り返し作業をテンプレート化して一発再現する仕組み

Agents: 複数のAIを同時に走らせてチームで分業する仕組み

Hooks: セッション開始時やツール実行前後に自動処理を仕込める

MCP接続: Notion、Slack、GitHub、Googleカレンダー等を直接操作できる

31-3. Claude Codeの弱み（正直に書きます）
Claude Codeはターミナルベースなので、指示しないとドキュメントやファイルを自動では作ってくれないことがあります。Cursorは会話の流れでファイルをどんどん作ってくれるけど、Claude Codeは「これ作って」と明示的に言う必要がある場面が多い。

ただし、これはSkillsで解決できます。「/記事生成」と打てばファイル生成まで自動でやる——そういう仕組みを一度作ってしまえば、以降は指示すら不要になります。

一言で言うと: Cursorは「速くて手軽」。Claude Codeは「仕組みを作れば最強だけど、最初の設計が必要」。

31-4. 初心者はVS Code + ターミナルから始めるのが一番いい
Claude Codeの起動方法はいくつかあります。

ターミナル単体: Mac/PCのターミナルから直接 claude と打つ

デスクトップアプリ: Claude Codeの専用アプリから起動

VS Code / Cursor / Antigravity: エディタのターミナルから起動

どれでも同じClaude Codeが動きます。機能の差はありません。

でも初心者には、VS Codeのターミナルから使うのが一番わかりやすいです。

理由は2つ。

① ファイルの変化が見える。 Claude Codeが作ったファイルや編集内容が、VS Codeの画面にリアルタイムで反映される。「何が起きているか」が見えるので安心感がある。

② 軽い。 Cursorは高機能ですが動作が重くなることがある。VS Codeは軽量で安定している。

VS Codeのターミナルで claude と打つだけ。拡張機能は不要です。シンプルが一番強い。

36-1. 🖥 開発環境（作業場のこと）
IDE: プログラムを書くための「作業机」。ペン・ノート・辞書・電卓が全部セットになった便利な机。家具が一通り揃ったキッチンみたいなもの

VS Code: Microsoftが作った無料のIDE。世界中のエンジニアが使う定番。Claude Codeはこの中で使うのが基本。CursorやAntigravityは「VS Codeを独自にカスタムしたバージョン」

開発コンテナ: 持ち運べる「作業部屋」。自分のPCにあれこれ直接入れると散らかるので、箱の中で作業する感覚。箱ごと人に渡せる

Docker: 開発コンテナを作る代表的な道具。「アプリを箱に詰めて配送する」技術。サーバーを引っ越すときも環境ごと運べる

36-2. ⚙️ 環境・設定（裏で効く設定のこと）
環境変数: プログラムに外から渡す「設定メモ」。パスワードやAPIキーをコードに直書きせず、外から差し込む仕組み

.env: 環境変数を書いておくファイル。見た目はただのメモ帳。Gitに上げないのが鉄則（漏れたら事故）

mkdir: ターミナルで「フォルダ作って」と命令するコマンド。make directory の略。Finderの「新規フォルダ」のコマンド版

rm: ターミナルで「ファイル削除して」のコマンド。remove の略。ゴミ箱を経由せず即消しなので注意

36-3. 📦 コード管理（履歴・共有のこと）
Git: ファイルの変更履歴を自動で記録する装置。「あの時点に戻したい」が後からできる。タイムマシンみたいなもの

GitHub: Gitの内容をクラウドに置ける場所。チームで共有できるし、PCが壊れてもデータが残る

.gitignore: 「このファイルはGitで管理しないでね」と書くリスト。.envや一時ファイル、巨大ファイルを除外する

36-4. 🏗 Webアプリの構造（アプリの骨格のこと）
フロントエンド: ユーザーから見える画面側（ボタン・文字・色）。ブラウザの中で動く部分

バックエンド: 画面の裏で動く処理。「データを保存」「計算する」「ログイン判定」など

フレームワーク: アプリの「雛形セット」。ゼロから組むと大変な共通部品を、誰かが既に作ってくれたもの（React、Next.js、Django等）

データベース: データを整理して保存する「電子的な棚」。ユーザー情報・商品・注文履歴などを入れておく

キャッシュ: よく使うデータを「手元に置いておく」仕組み。毎回遠くから取ってくると遅いので、近場にコピーを置く

API: アプリ同士が会話するための「窓口」。「このURLに投げると、この形で返事がくる」というルール表

36-5. 🌐 ネットワーク（通信のこと）
Cookie: ブラウザに保存される小さなメモ。「ログイン状態」「前回見たページ」などを覚える用

IPアドレス: インターネット上の住所（192.168.1.1 みたいな番号）。どのマシンと通信するかを示す

DNS: 人間が覚えやすいドメイン名（google.com）を、機械が使うIPアドレスに翻訳する仕組み。電話帳みたいなもの

SSH: サーバーに安全にログインするためのトンネル。「パスワードより鍵」が今の主流

FTP: ファイルをサーバーに送受信する古い方法。今はSSH系が主流だが、レンタルサーバーで現役

36-6. 🔐 セキュリティ・本人確認
暗号化: 情報を「鍵がないと読めない形」に変換すること。郵便を金庫に入れて送るイメージ

秘密鍵: 暗号を解ける「マスターキー」。他人に見せたら終わり。.envや~/.sshに厳重保管

トークン: 「あなたが本人である」証明書の電子版。ログインすると発行される。※AI文脈では別の意味もあり：AIが文章を処理する最小単位（文字に近いが文字そのものではない）

36-7. 🚀 公開・運用
デプロイ: 作ったアプリをサーバーに載せて「世界に公開する」作業。ローカルで動くだけの状態から、URLで誰でもアクセスできる状態にする

デバッグ: バグ（不具合）を見つけて直す作業。「どこで壊れた？」を突き止める探偵仕事

ログ: プログラムが残す「行動記録」。「10:30にエラーが出た」「このユーザーがログインした」など、トラブル調査の証拠になる

45. CH.5 「プロンプトが9割」は嘘

まず、世の中に出回っている「プロンプトが9割」系のノウハウについて、はっきり言います。

あれは嘘です。

正確に言うと、2023年には正しかった。でも2026年の今、プロンプトの工夫だけで差がつく時代は終わりました。

なぜかと言うと、Chain of Thought（段階的に考えさせるテクニック）ってありますよね。2022年に登場して革命的だった。でも2026年の最新モデルに使うと、むしろ遅くなるだけです。レスポンスが35〜600%増加して、精度はほぼ変わらない。最新のAIは指示しなくても勝手に深く考えるようになったからです。

つまり、プロンプトテクニックには「消費期限」がある。今日学んだテクニックが半年後には不要になる。

じゃあ何を学べばいいのか。プロンプトの「先」にあるもの——コンテキストエンジニアリングです。

46. プロンプトエンジニアリングの基本
プロンプトエンジニアリング自体を否定しているわけじゃないです。基礎としては必要です。ただ、ここで止まるなということ。

まず基本テクニックを整理します。

各テクニックの具体的なプロンプト例やテンプレートは、特典③「プロンプト集」で場面別にまとめて配布しています。ここでは「何があるか」を把握しておいてください。

47. ゴールシークプロンプト — AIに「質問させる」
プロンプトエンジニアリングの中でも特に面白い手法を1つ紹介します。これはClaudeCodeでよく使うので使えるようにしてください。

ゴールシークプロンプト。

通常のプロンプトは「ユーザーがAIに指示を出す」一方通行です。ゴールシークは逆。AIがユーザーに質問する。

通常:

私: 「ブログ記事を書いて」

AI: [曖昧な記事が出てくる]

ゴールシーク:

私: 「ブログ記事を書く。必要な情報を質問して」

AI: 「①読者は？ ②テーマは？ ③文字数は？ ④キーワードは？」

私: [各質問に回答]

AI: [精度の高い記事が出てくる]

なぜ効くのか。 人間は「自分が何を欲しいか」を正確に言語化できないことが多い。でもAIに質問されると、答えながら頭が整理される。結果、AIが受け取る情報の質が上がる。

47-1. テンプレート
あなたの目標は、私のニーズに合わせて最高の成果物を作ることです。

次のプロセスに従ってください。

まず、何を作りたいかを確認してください。

私の回答をもとに、以下の3つを生成してください。

a) 改訂された計画案

b) 改善提案

c) 追加質問（まだ必要な情報があれば）

私が「完了」と言うまで、2を繰り返してください。

私はこのゴールシーク的なアプローチを、Claude CodeのSkillsに組み込んでいます。たとえば「/記事生成」と打つと、まずAIが「テーマは？ターゲットは？トーンは？」と聞いてくる。答え終わったら自動で記事を生成する。

指示を出す前に、AIに「聞くべきことを聞かせる」。 この発想が、プロンプトエンジニアリングの中で最も価値がある部分です。

48. プロンプトの限界


— なぜ「9割」ではないのか

ここまで読んで、「じゃあプロンプトは大事じゃないか」と思ったかもしれません。

大事です。でも「9割」じゃない。

理由は3つ。

① テクニックに消費期限がある。 Chain of Thoughtは2022年に革命だったのに、2026年には最新モデルに不要。今日学んだテクニックが半年後に使えなくなるリスクがある。

② 毎回打ち直す構造が非効率。 どんなに優れたプロンプトも、毎回コピペしている時点で効率の限界がある。ファイルに書いておけば二度と打たなくて済む。

③ 蓄積しない。 プロンプトは「今この瞬間の指示」。次のセッションでは消えている。ビジネスの知識やルールが蓄積されない。

プロンプトエンジニアリングは入口です。でもそこで止まると、永遠に「毎回ゼロから説明する人」のままです。

53. 「AIっぽさ」を消す方法
Projects機能を使い始めると、最初に気になるのが「AIっぽい出力」です。

「多くの人が〜」「〜は重要です」「さらに」「また」「加えて」——こういう表現が出てくる。

これを消すには、カスタムインストラクションに「やるな」リストを入れるのが一番効きます。

54. 禁止表現
「多くの人が〜」「〜は重要です」などの抽象的な一般論

「まず/次に/さらに/結論として」の接続詞連打

「あなた、」で始まる文（翻訳調）

「未来へはばたく」「羅針盤」「旅路」などの大げさな比喩

文の長さが均一になること（短文と長文を混ぜる）

やっていいことを書くより、やってはいけないことを書く方が効果が高いです。AIは「こう書け」より「これは書くな」の方が正確に守ります。

ただしAnthropicの公式推奨は「否定形より肯定形で代替を示す」こと。

❌ 「マークダウンを使わないで」

✅ 「回答は滑らかな散文で書いてください」

否定形が曖昧に解釈されるリスクがあるため、「〜するな」より「代わりに〜しろ」の方が安定します。

55-1. ステージ1: プロンプトエンジニアリング
定義: 1回の指示文（プロンプト）を工夫して、AIから最大の出力を引き出す技術。

定義: AIが参照する「環境（文脈）」そのものを設計する技術。プロンプトではなく、プロンプトの外側を整える発想。

目的: 毎回の指示を短くしても、AIが勝手に良い答えを出す状態を作る。

代表的な手段:

rules/: 安全ルール・文体ルール・判断基準をファイル階層で管理（CH.9）

memory/: 使うたびに賢くなる永続記憶（CH.14）

MCP接続: Notion・GitHubといった外部ツールを文脈に取り込む（CH.12）

到達できる場所: 「毎回初対面の新入社員」が「自分のビジネスを知っているメンバー」に変わる。指示が「ブログ書いて」の3文字で済むようになる。

限界（ここで止まる理由）:

人間がトリガーを引かないと動かない（毎回Claudeに話しかける必要がある）

判断・実行の主導権が人間側にある（AIは応答する側）

並列作業が自分の画面1つに縛られる

55-3. ステージ3: ハーネスエンジニアリング
定義: AI自身が自走する枠組み（harness = 馬具・装具）を設計する技術。「AIが応答する側」から「AIが勝手に動く側」への反転。

目的: 人間が指示しなくても、AI群が自動で判断・実行・完了報告まで回す環境を作る。

代表的な手段:

Subagents: 専門エージェントを複数立てて、並列分業（CH.11）

Hooks: セッション開始時・ツール実行前後に自動発火する処理（CH.13）

MCP統合: 外部ツール（Notion・Slack・GitHub等）をAI自身が操作（CH.12）

なぜ「ハーネス」と呼ぶか: 馬に装着する馬具のように、AIの能力を特定の方向に誘導するフレームワークを組む発想だからです。プロンプト＝鞭、コンテキスト＝鞍、ハーネス＝馬車全体。到達する距離が段違いに変わります

56. CH.6 Artifacts活用術
動画解説：


Claude ChatにはArtifactsという機能があります。

Artifactsは「会話の中で、コード・HTML・文章・図解をその場で生成して、別ウィンドウに表示する」機能です。チャットの返答とは別に、独立したパネルにプレビューが出る。

これが何に使えるかというと、プロトタイプを爆速で作れる。

57. Artifactsでできること
HTML/CSSのプレビュー: LPやダッシュボードの構成案をその場で確認できる

コードの生成と表示: Python、JavaScript等のコードをシンタックスハイライト付きで表示

Markdownドキュメント: 構成案や企画書をその場で整形

SVG/図解: シンプルな図解やフローチャートを生成

重要なのは、「見ながら会話で修正できる」こと。「ここの色を変えて」「この項目を追加して」と言えば、Artifactsがリアルタイムで更新されます。

58. Artifactsの起動 — どこを触れば発動するか
Artifactsは自動発動と明示的な依頼の2パターンで使えます。

65. CH.7 アダプティブ思考 — Claudeに「考えさせる」技術
Claudeにはアダプティブ思考という機能があります。



アダプティブ思考

通常のClaudeは、質問を受けたらすぐに回答を生成し始めます。アダプティブ思考をオンにすると、回答の前に「考える時間」を取る。

たとえるなら、普通のClaudeは「聞かれたら即答する優秀な人」。アダプティブ思考をオンにしたClaudeは「聞かれたら一度黙って考えてから答える人」。

即答が正しい場面もあれば、じっくり考えた方がいい場面もあります。

66. 使うべき場面
アダプティブ思考が威力を発揮するのは、「答えが1つじゃない」問題です。

戦略設計: 「このビジネスの北極星は何か」「このオファーの弱点はどこか」

複雑な分析: 「この3つの選択肢のメリット・デメリットを構造的に比較して」

長文の構成設計: 「3万字のガイドの構成を設計して」

反論の先回り: 「このセールスページに対する購入者の不安を10個挙げて」

コードのアーキテクチャ設計: 「このシステムの全体構成を考えて」

共通点は「表面的な答えではなく、構造を考える必要がある」タスクです。

私自身、このガイドのブランドの核心——「努力ではなくAIと仕組みで勝たせる」というコアメッセージは、Claude Opusのアダプティブ思考で言語化した。自分の頭の中にぼんやりあった方向性を、Claudeに深く考えさせることで一文に結晶化できた。

67. 使わなくていい場面
逆に、アダプティブ思考が不要な場面もあります。

単純な質問: 「この関数の使い方は？」「この単語の意味は？」

定型作業: 「この文章を箇条書きにして」「このCSVをJSON形式に変換して」

スピード重視: 大量のタスクを次々処理したいとき

こういう場面でアダプティブ思考をオンにすると、ただ遅くなるだけです。考える必要がないのに考えさせている状態。

68. 実践のコツ
68-1. Claude Chatでの使い方
Claude Chatでは、モデル選択ドロップダウンからアダプティブ思考対応モデル（Opus等）を選ぶだけ。特別なキーワードは不要で、複雑な質問には自動で深い推論が走ります。入力欄上部の思考インジケーターで「今考えている」状態が視認できます。

質問を投げる前に「戦略レベルの問いか」「単純な情報取得か」を判断してモデル切替する運用がシンプルです。

68-2. Claude Codeでの使い方はCH.14で
Claude Code（CLI）で思考制御する具体手段——ultrathink キーワード、/effort コマンド、プランモード（Shift + Tab 2回）、/model 切替——これらはCLI固有の話なので CH.14「Memory・コマンド・コスト管理」で詳しく解説 します。

本章で押さえてほしいのは「考えさせるべき場面を判断する」という設計の考え方そのもの。細かいCLI仕様はCH.14で戻ってきてください。

場面 | 推奨

71. CoworkとClaude Codeの関係

まず、ここを正確に理解しておいてください。

CoworkとClaude Codeは別製品です。

同じAnthropicが作った兄弟のような関係ですが、対象ユーザーが違います。

Claude Code Cowork

公式の言い方を借りると、「Cowork = Claude Codeの力を、コードなしで使えるようにしたもの」。

誕生の経緯も面白い。Claude Codeをリリースしたら、エンジニアだけじゃなくPMやマーケターまで使い始めた。「これ、コードを書かない人にも使えるようにした方がいいんじゃないか」——そうやって生まれたのがCoworkです。

スマホがトランシーバーみたいに、PCに指示を飛ばす感覚です。

セットアップ手順（初回のみ）

Dispatchはスマホ↔PCのペアリングが必要。初回だけ少し手間がかかります。

PC側（Claude Desktop）:

Coworkタブを開く

左上の 「Dispatch」

「スマートフォンと連携する」 をクリック

ペアリング用QRコードが表示される

スマホ側（Claudeモバイルアプリ）:

App Store / Google Play から 「Claude」 公式アプリをインストール（まだの場合）

同じアカウントでログイン

タブバーの 「Dispatch」 をタップ

「Pair with computer」 を選択

PC側のQRコードをスマホで読み取る

「Paired successfully」と出れば完了

これで双方向の接続が開通します。同一アカウントでログインしていることが条件。

Claudeモバイルアプリを起動

Dispatchタブを開く

接続先PCを選択（複数台登録できる）

メッセージを入力して送信するだけ

私の使い方の例：

通勤電車: 「昨夜のメール全部読んで、返信必要なのだけリスト化して」

昼休み: 「昨日のZoom議事録から、決定事項とアクションアイテムを抽出してNotionに追記」

子供を送ったあと: 「午後の打ち合わせ資料のアウトラインを作って、15分で読める形で」

ジム帰り: 「今週のX投稿5本のネタを、伸びてる競合投稿を参考に下書きしといて」

朝の通勤中に投げた指示が、家に着く頃には完了している。これが日常になると、作業の前倒しが3〜4時間単位で効いてきます。

制限事項

PCが起動中 + Claude Desktopが開いている間のみ動作（これが最重要）

スマホで結果をそのまま確認できる（テキスト系なら）

ファイル成果物はPCのフォルダに保存される（スマホからは直接触れない）

Mac miniを1台「Dispatch常駐専用機」として常時起動させる人も増えてます。電気代は月数百円なので、ROIは余裕でプラス。

73-5. ⑤ Computer Use — 画面を直接操作する
ブラウザを開く、ボタンをクリックする、テキストを入力する——PCの画面をClaudeが直接操作する機能です。

何ができるか

API連携がない（＝MCPで繋げない）サービスでも、画面を見てそのまま操作することで自動化できます。

古いWeb業務システム: APIがない旧式の受発注ツールを、ブラウザごとClaudeに操作させる

デスクトップアプリ: Excel、Photoshop、Figmaなど、APIが貧弱なアプリを自動化

フォーム大量入力: ECサイトの商品登録、銀行振込フォーム、税務ソフトなど、人間がやると苦痛な反復作業

競合スクレイピング: スクロール・クリックが必要な動的ページから情報収集

Computer Useを有効にする手順

Claude Desktop → 「Settings」 → 「一般」

「コンピュータ使用」 をON

初回は macOS なら システム設定 → プライバシーとセキュリティ → アクセシビリティ で Claude Desktop に画面操作の許可を与える必要がある（ダイアログが出るので従うだけ）

Windows なら管理者権限の確認が走る

これで Claude が画面を見て操作できる状態になります。

具体的な流れ

「ブラウザでこのURL開いて、スクショを取って」と指示

Claudeがスクリーンショットを取り、画面を解析する

マウス移動・クリック・キーボード入力を1つずつ実行

途中経過をテキストで報告しながら進む

完了すると「終わりました」と通知

人間が操作するのを少し遅い速度でAIがやっている感覚です。動作中は画面が勝手に動くので、別画面で作業するか、放置しておくのが吉。

途中で止めたいとき

Claude Desktop上部に 「Stop」 ボタン、またはキーボードの Esc を押すと、進行中のComputer Use操作を即時停止できます。暴走が怖いときは片手をEscに置いて見守るのが最初のうちの正しい姿勢。

リスクと対策

Computer Useは強力ですが、リスクもあります。

リスク | 対策

決済・送金・削除系の操作は、Computer Useでは絶対にやらないのが基本姿勢。これは本編CH.15（セキュリティ）でも繰り返し触れます。

79. まず概念 — CLAUDE.mdは「会社の定款」

CLAUDE.md = 定款（会社の基本方針）

rules/ = 就業規則（やっていいこと・ダメなこと）

agents/ = 部署（マーケティング部、ライティング部、分析部…）

80. コンテキスト = 部屋の整理


image2

もう1つ、大事な概念を先に伝えます。

Claude Codeが会話中に拾う情報量のことをコンテキストと呼びます。これは部屋の広さだと思ってください。

散らかった部屋（情報が整理されていない状態）では、必要なものが見つからない。AIも同じで、コンテキストが散らかっていると、必要な情報を拾い損ねる。

コンテキスト衛生チェック: Claude Codeで /context と打つと、現在のコンテキスト使用量が見えます。何も会話していない状態で2割を超えていたら、CLAUDE.mdやスキルが長すぎるサイン。整理が必要です。

84-1. 私の実例
私の文体ルールには、たとえばこういうことが書いてあります。「抽象論」「AI特有のつなぎ方」「翻訳調の日本語」を排除する具体例です。

## トーン
- カジュアルでありながら知的（友人と話すような距離感 + 正確な語彙）
- 断定→理由→救済→一手の4段構造で書く
  例: 「それ、やめたほうがいい（断定）。
      なぜなら〜だから（理由）。
      でも代わりに〜すればOK（救済）。
      今日は〜から始めてください（一手）」

## 禁止表現
- 「多くの人が〜」「一般的には〜」などの抽象的一般論
- 「まず、次に、さらに、そして」の接続詞連打
  → 代わりに: 「で、」「しかも」「あと」で短く繋ぐ
- 翻訳調の比喩:「〜のようなもの」「〜と言えるでしょう」「〜ですね」
- 「いかがでしたか」「まとめ」「おすすめです」のような締め

## 必須表現
- 数字で示せるものは数字で（「たくさん」「多くの」→「127件」「82%」）
- 一人称は「私」で統一、「僕」は禁止
- 過去の体験談は「である」調、説明は「ですます」調
これをrules/に入れた瞬間から、Claudeの出力が激変した。「AIっぽさ」が一気に消えた。実際に使っている私のvoice-guideは40項目以上ありますが、最初は上のような5-10項目だけで十分効きます。

87-1. なぜ「200行以下を目安」にするのか
私は最初、1ファイルに全部詰め込んでいました。CLAUDE.md、ルール、ナレッジ、過去の学び——全部1つのファイル。

やってみてわかったのは、長くなるほど指示の追従性が下がること。ファイル自体は全文ロードされるのですが、情報が膨大になると後半のルールが体感的に効きにくくなる、という現象に何度も遭いました。

公式ドキュメントでも「CLAUDE.md は200行以下を目安に」と推奨されています。強制的な上限ではなく、AIが集中して従える分量の目安です。私の体感ともこの目安は一致しています。

だから長くなったらrules/に分離するのが正解。骨格（判断基準）だけCLAUDE.mdに残し、詳細はrules/やknowledge/に分散させる設計です。

補足: 起動時に先頭200行または25KBで物理的に切断されるのは auto memory の MEMORY.md 側（CH.14で詳述）。CLAUDE.md 自体は切断されず全文ロードされるので、「200行を超えると後半が消える」は誤解です。ただし長すぎると追従性が落ちる体感はあるので、目安として意識する価値はあります。

88. 自己更新メモリ — 使うたびに賢くなる
Claude Codeのメモリには大きく2種類の運用があります。最初にその違いを押さえてください。

88-1. ① 公式 auto memory（machine-local）
Claude Codeには公式の auto memory 機能が組み込まれています。保存場所は：

~/.claude/projects/<project-name>/memory/MEMORY.md

ここに Claude が自動で記録を追加し、次のセッションで先頭を自動でコンテキストに読み込みます。ホームディレクトリ配下なのであなたのPCに固有（machine-local）で、他人と共有されません。

保存先（autoMemoryDirectory）は user / local settings からのみ変更可能で、プロジェクト内のsettings.jsonでは上書きできません。つまり公式 auto memory はスターターキットに同梱して配布する仕組みではありません。

88-2. ② 自作メモリ運用（プロジェクト内に記録・Gitで共有可能）
一方で、スターターキットには projects/memory/ ディレクトリが入っています。これは公式 auto memoryではなく、プロジェクト内にメモリを置いて Git で共有する自作運用です。

保存場所: プロジェクト内の .claude/projects/memory/MEMORY.md

プロジェクト固有の「判断ログ」「ユーザーの好み」「過去の失敗」などを手動 or Claude経由で蓄積

Git に含めればチームや購入者と共有できる

私は両方を併用しています。「PCローカルの癖」は auto memory に、「プロジェクトの判断基準」は自作メモリに、という使い分けです。

88-3. メモリを育てるコツ
どちらの形式でも、Claudeに「今の判断をメモリに記録して」と頼むと追記してくれます。「この人は箇条書きより表形式を好む」「この指示には必ずこう答える」——こういうことが蓄積されていく。覚えてほしいことは定期的に入れさせるのが習慣化のコツです。

次のセッションで起動したとき、この記憶を持った状態で始まります。使えば使うほど、あなたのAIチームが賢くなる。

ただし、公式 auto memory の MEMORY.md は起動時に先頭200行または25KB（どちらか先に到達した方）で切断される仕様があります（詳細はCH.14）。長くなったらサブファイルに分割する必要があります（「MEMORY.mdを整理して」と頼めばやってくれます）。

99. エージェントとは — 専門家を雇うということ


image6

CH.9で「部署を作る」話をしました。マーケティング部、ライティング部、リサーチ部——あなたのビジネスに必要な部署を設計した。

でも部署を「定義しただけ」では何も起きません。実際に仕事を振る必要があります。

エージェントとは、Claude Codeの中で動く「専門家キャラ」です。

たとえば「X投稿を書いて」と頼むとき、普通のClaude Codeに頼むのと、「X専門家エージェント」に頼むのでは、出力の質が全然違います。

なぜか。エージェントには専用のルール・参照するナレッジ・判断基準が設定されているからです。

普通のClaude Codeは「何でもそこそこできる汎用社員」。 エージェントは「その分野に特化した専門社員」。

100. 1エージェント = 1役割
これが最重要ルールです。

1つのエージェントに複数の役割を持たせないでください。

「マーケティングもライティングもやるエージェント」は作らない。兼務させると、AIがどの役割で動いているか判断できなくなって、出力がぶれます。

人間の会社でも同じですよね。営業と経理を1人に兼務させたら、どっちも中途半端になる。

最初は3部署で十分。 使いながら「この仕事が溢れてる」と感じたら、その時に部署を追加する。

101. エージェントの呼び出し方
Claude Codeでエージェントを使うには、2つの方法があります。

101-1. 方法1: 名前を指定して呼ぶ

@ の後にエージェント名を入れると、そのエージェントが応答します。

101-2. 方法2: Claudeに任せる
X投稿を3パターン考えて

CLAUDE.mdやrules/に「X投稿はマーケティング部が担当」と書いてあれば、Claude Codeが自動で適切なエージェントにルーティングしてくれます。

102. 並列実行 — チームで分業する

普通にClaude Codeを使うと、1つのタスクを順番にやっていきます。「X投稿を書いて」→ 完了 →「note記事を書いて」→ 完了。

エージェントを使うと、複数の仕事を同時に走らせられます。

X投稿担当、note担当、LINE配信担当を同時に走らせて、

今週のコンテンツを一括で作って

103. エージェントごとにモデルを指定する — コスト最適化の鍵
エージェントには個別にモデルを指定できます。これがコスト最適化の鍵です。

考え方はシンプル。思考する指揮官だけOpus、他はSonnetで十分。

やり方は簡単です。agents/*.mdのfrontmatter（ファイル冒頭の --- で囲まれた部分）に model: を1行追加するだけ。

name: strategist

description: "戦略設計・意思決定を担当する指揮官"

model: opus

name: writer

description: "記事・SNS投稿を担当するライター"

model: sonnet

これだけで、戦略エージェントはOpusで、ライターはSonnetで自動的に動きます。

全部Opusで走らせると課金が一瞬で吹き飛びます。 「考える仕事」と「作る仕事」を分けて、モデルを使い分ける。これが私のAI会社のコスト設計です。

104. コンテキスト継承の罠
ここは少し技術的な話ですが、大事なことです。

サブエージェントに自動で渡るものと渡らないものがあります。

つまり、エージェントは「会話の流れ」は知りません。 「さっき話してたやつ」は通じない。エージェントにはタスクの目的・必要な情報・参照ファイルを毎回明示的に渡す必要があります。

これを知らないと「サブエージェントが全然使えない」と感じます。使えないんじゃなく、渡し方が間違っているだけです。

105. 「専門書を専門家が持ち歩く」構造
エージェントを設計するときの理想的な考え方があります。

「専門書を専門家が持ち歩く」——つまり、エージェント（専門家）が自分の担当分野のナレッジ（専門書）を持っている状態を作る。

たとえば：

X専門家エージェント → フック設計プレイブック・X長文プレイブックを参照

ライティングエージェント → 文体ルール・AIっぽさ除去ガイドを参照

リサーチエージェント → 競合分析フレームワーク・市場調査テンプレートを参照

CH.10のSkillsと組み合わせると最強です。「X専門家エージェントが、X投稿生成スキルを実行する」——専門家が業務マニュアルに従って仕事をする構造。

CH.12 MCP・Git連携

ここまでで、あなたのAI会社には定款（CLAUDE.md）、就業規則（rules/）、業務マニュアル（Skills）、部署（Agents）が揃いました。

108. MCPとは — Claudeの「手足」
MCP（Model Context Protocol）は、Claude Codeを外部ツールに接続する仕組みです。

たとえば：

Notion MCP → ClaudeがNotionのページを直接読み書きする

Slack MCP → Claudeがチャンネルにメッセージを送る

GitHub MCP → Claudeがリポジトリを操作する

普通なら「Claudeで作った文章をコピーして、Notionに貼り付けて…」という手作業が必要です。MCPを繋げると、「Notionに入れて」の一言で終わる。

コピペの往復がゼロになる。これだけで日常の作業スピードが体感で2倍になります。

109. scope — どの範囲で使うか
MCPを設定するとき、scope（範囲）を選ぶ必要があります。

迷ったら user で設定してください。 後から変更もできます。

APIキーはコマンドに直書きせず、.envファイルに書いて環境変数として読み込ませるのが基本です。直書きするとシェルのヒストリーに残り、漏洩リスクになる。

# 1. プロジェクトルートの .env にAPIキーを書く
# .env
GITHUB_PERSONAL_ACCESS_TOKEN=ghp_xxxxxxxxxxxxxxxxxxxx
# 2. .env を読み込んだ状態でMCP登録
export $(cat .env | xargs)
claude mcp add github --scope user --env GITHUB_PERSONAL_ACCESS_TOKEN
.env は必ず .gitignore に追加してください。GitHubに上げると秘密情報が公開される事故になります。

設定が完了したら /mcp コマンドで接続状態を確認できます。

112. コンテキスト衛生の注意

MCPのスキーマも毎回コンテキストに読み込まれます。 つまり、使っていないMCPを繋げっぱなしにすると、部屋が散らかる。

使っていないMCPはオフにしてください。 /context コマンドで使用量を確認して、2割を超えていたら整理のサインです。

Claude CodeはGitとネイティブに連携しています。MCPを入れなくても最初から使える機能です。「コードを壊したらどうしよう」という不安を消してくれる安全装置だと思ってください。

113-1. チェックポイント — 「やっぱり戻したい」が1秒で叶う
Claudeが大きな変更を加える前に、自動でセーブポイントを作ります。ゲームで言う「セーブして次の戦闘に挑む」と同じ。

もし修正後に「やっぱり前の方がよかった」「何か動かなくなった」となっても、チェックポイントに戻すだけで元通り。1秒で巻き戻せます。

使い方の例: 「このファイル全体を書き直して」と頼むと、Claudeが自動で .claude/checkpoints/ にスナップショットを保存。変更後「戻して」と言えば、その時点に復元されます。

これがあるから、Claude Codeに大胆な修正を任せられます。「失敗しても戻せる」を知っているから、試行錯誤のスピードが上がる。

113-2. ブランチ運用 — 複数タスクを安全に並行
Gitのworktree機能を使うと、同じプロジェクトに対して複数の作業ブランチを同時に開ける。

具体例:

メインブランチで「LPのコピー執筆」を進める

同時に別ブランチで「新機能の試作」をClaudeにやらせる

どちらかが失敗しても、もう片方には影響しない

「メインの仕事を止めずに、別の実験も走らせたい」ときに便利です。

113-3. commit/pushの自動化 — 「保存して」の一言で終わる
Claudeに「コミットして」と言えば、変更内容を自動で記録。「プッシュして」と言えばGitHubに送ります。コミットメッセージも文脈から自動生成される。

安全設計: force push（過去の履歴を上書きする危険なコマンド）は確認なしに実行しません。ミスでチーム全員の履歴を吹き飛ばす事故を防ぐ仕組みです（rules/01-safety.mdで制御）。

114. APIの基礎 — MCPの裏側で何が起きているか
MCPを使いこなすには、APIとAPIキーの仕組みを最低限だけ理解しておく必要があります。難しい話ではありません。

114-1. APIとは「窓口」のこと
APIは「Application Programming Interface」の略ですが、用語は忘れてOK。

イメージは役所の窓口です。NotionやGitHubという「役所」に行って、「このページ読みたい」「このファイル書き換えたい」と申請する。窓口（API）がその申請を受け取り、内部の情報を返してくれる。

MCPは、Claudeがその窓口に並んでくれる代理人です。あなたは「Notionに入れて」と言うだけ。裏でMCPがNotion APIの窓口に並び、書き込み申請を出し、結果を持って帰ってくる。

114-2. APIキーは「社員証」
窓口に並ぶとき、「あなた誰ですか？」と聞かれます。そのときに見せる社員証がAPIキー（アクセストークン）です。

Notion → Integration Token

GitHub → Personal Access Token（PAT）

Slack → Bot Token

Anthropic（Claude自体のAPI） → API Key

どれも「長い英数字の文字列」です。これを持っていないと、MCPはサービスに入れません。

114-3. APIキーの管理ルール（最重要）
APIキーは銀行のカード番号と同じ扱いをしてください。

私の運用: .envファイルを1つ作って、そこに全APIキーを列挙しています。.gitignoreで必ず除外。Claude Codeには「.envを出力しないで」とrulesに書いています（CH.7で触れたfeedback_no-secrets-output.mdがこれ）。

114-4. 料金が発生するAPIに注意
APIは従量課金のものがあります。特に：

Anthropic API（Claude自身を別経由で叩く場合）: 1トークン単位で課金

画像生成API（fal.ai、OpenAI DALL-E等）: 1枚ごとに課金

OpenAI API: 同じく従量

Notion/GitHub/Slackは個人利用なら基本無料。でも画像・動画系APIは財布が溶ける速度で課金されます。私も以前、ループを止め忘れて$100飛ばしたことがある。

対策: MCPを繋げる前に、料金体系を1行でいいから確認する。これを習慣にしてください。

自動化できない部分が3つあります。ここは自分で決めてください。

PATのscope: repo（public/private両方対象）にするか、public_repoだけにするか。private repoも操作したいならrepoが必須

有効期限: 90日 or No expiration — 90日ローテーション推奨。No expirationは漏れたら永久に危険

Private / Public repo: 事業情報が入るCLAUDE.mdをpushするなら必ずPrivate

あと、pushする前に.gitignoreに.envが含まれているか、自分の目で必ず確認してください。ここだけは「AIに任せた」で済ませない。漏れたら即revokeです。

115-3. よく詰まるポイント（症状を伝えれば直せる）
private repoが見えない: PATのscopeにrepoが入っていない → 「private repoが見えない」と伝える

pushが403エラー: ローカルのGITHUB_TOKEN環境変数がPATと衝突 → 「403が出た」と伝える

organization配下が操作できない: organizationの管理者がThird-party accessを許可する必要あり

人がやるのは「症状を正確に伝える」ことだけ。直し方はAIが知っています。

115-4. PATの更新を忘れない
90日で期限切れになると、全MCP操作が止まります。85日後のリマインダーをカレンダーに入れておくのが吉。期限が近づいたらClaudeに「PAT更新したい」と伝えれば、新しいPATの発行と.env差し替えまで案内してくれます。

122-1. 進め方 — 導入ドキュメントをClaudeに渡す
Claude Codeを起動した状態で、次のドキュメントをそのまま貼り付けてください。

Claude Code に `rm -rf` コマンドを止めるフックを仕込みたいです。

【やりたいこと】
- PreToolUse フックで Bash ツール呼び出しを検知
- コマンドに `rm -rf` が含まれる場合、実行前に自動でブロック（exit 2）
- ブロック時にメッセージを標準エラーに出力

【進め方の希望】
1. スコープの確認
   - プロジェクト限定（.claude/settings.json）か、全プロジェクト共通（~/.claude/settings.json）か
   - 今回はプロジェクト限定で進めたい
2. .claude/settings.json に PreToolUse エントリを追加
   - 追加する内容を見せてJSON構文をチェックしてほしい
   - 既存のsettings.jsonがある場合は既存内容を壊さないようマージ
3. .claude/hooks/block-rm.sh を作成
   - 中身のshell構文を見せてチェックしてほしい
   - `chmod +x` で実行権限を付与
4. テスト実行
   - `rm -rf /tmp/test-delete-me` で止まるか確認（実ファイルではなく安全なパスで）
   - `ls -rf` のような無関係コマンドは通るか確認
5. `/hooks` で Claude Code にフックが認識されているか確認

【気をつけたいこと】
- 最初は `rm -rf` だけに絞る（ブロック範囲を広げすぎて日常作業が止まるのを避けたい）
- settings.jsonのJSON構文エラーでセッションが立ち上がらなくなるのが怖い
  → 作ったあと必ず1回 Claude Code を再起動して正常起動を確認したい
- block-rm.sh の中身は shell script なので、改行や引用符の構文ミスに注意してチェックしてほしい
Claudeはこの流れで動きます。

「どのスコープに入れますか？ プロジェクト限定？ 全プロジェクト共通？」

「.claude/settings.json に PreToolUse を追加します。内容を見せるので確認してください」

「.claude/hooks/block-rm.sh を作って実行権限を付けます（chmod +x）」

「試しに rm -rf /tmp/xxx を打って止まるか確認しましょう」

実際にClaudeが生成するファイルはこんな形です。

{
  "hooks": {
    "PreToolUse": [
      { "matcher": "Bash", "hooks": [
        { "type": "command", "command": "$CLAUDE_PROJECT_DIR/.claude/hooks/block-rm.sh" }
      ]}
    ]
  }
}
#!/bin/bash
# 標準入力でツール情報のJSONが渡ってくる
COMMAND=$(jq -r '.tool_input.command' < /dev/stdin)
if echo "$COMMAND" | grep -q 'rm -rf'; then
  echo "rm -rf はブロックしました" >&2
  exit 2  # 2 = ブロック
fi
exit 0  # 0 = 通す
仕組みはシンプルです。フックは標準入力でツール情報のJSONを受け取り、終了コード（exit code）で結果を返すだけ。

122-2. 人が判断すべきこと
AIに任せていいのが9割だけど、自分で決めるポイントが2つあります。

スコープ: プロジェクト限定（.claude/settings.json）か、全プロジェクト共通（~/.claude/settings.json）か。迷ったらプロジェクト限定が安全

ブロックするコマンドの範囲: rm -rfだけか、git push --forceやgit reset --hardも含めるか。広く取りすぎると日常作業が止まるので、最初は1つから始めるのが鉄則

123. exit codeの使い分け
フックスクリプトの終了コードには意味があります。

「このコマンドは危ないから止めたい」なら exit 2。これだけ覚えればOK。

より細かい制御（特定の条件で許可/拒否/確認を分岐）は、JSONを返すやり方もあります。「もっと複雑な条件で分岐したい」とClaudeに伝えれば、JSON返却方式で書き直してくれます。

Claude Codeで /hooks と打つと、現在仕込まれているフックの一覧が出ます。どのイベントに何が設定されているか見える化されるので、「あれ、このフック効いてる？」と不安になったときは必ず確認してください。

126-1. MEMORY.md は「先頭200行または25KB」で切断される
公式 auto memory のインデックスファイル（~/.claude/projects/<project>/memory/MEMORY.md）は、セッション開始時に先頭200行または25KBのどちらか先に到達した方で切断されてコンテキストに読み込まれます。つまり後半は読まれません（これはCLAUDE.md側の「目安」ではなく、MEMORY.md側の物理的な仕様）。

長くなったら：

サブファイルに分割してくれる

MEMORY.mdは索引（目次）だけにする

これもCH.9の「コンテキスト衛生」の一部です。メモリが散らかると、Claudeが必要な記憶を拾い損ねます。

補足: CLAUDE.md側は全文ロードされるので、この200行/25KBの切断はかかりません。CLAUDE.mdで言う「200行以下を目安」は公式推奨の目安であり、強制的な切断ではないです（CH.9の補足参照）。同じ「200行」という数字でも、意味が違うので混同しないのがポイント。

127-4. 出力スタイル — 「コマンド」ではなく「ルール」として持つ
Claude Codeには、口調や出力形式を変えるための「出力スタイル（Output Style）」という仕組みがあります。これはコマンドではなく、フォルダに置くルールファイルとして管理します。

置き場所は2種類。

個人用: ~/.claude/output-styles/ （全プロジェクト共通）

プロジェクト用: .claude/output-styles/ （そのPJ限定）

中身はフロントマター付きのMarkdownファイル。たとえば「モモンガ口調で返してほしい」なら .claude/output-styles/momonga.md にこう書きます。

name: momonga

description: モモンガ口調で返答する

Custom Style Instructions

あなたはモモンガです。「〜だよッ」「〜ゾ！」を語尾に混ぜ、

ふてぶてしさ7割+かわいさ3割のトーンで応答してください。

切り替えは /config → Output style から選ぶか、settings.json に "outputStyle": "momonga" と書くだけ。次にセッションを起動したときから適用されます。

なぜコマンドで切り替えないのか: 出力スタイルはセッション全体のシステムプロンプトに入る設定です。会話中にコロコロ変えるものではなく、プロジェクトの性格として固定して使うもの。だからフォルダに置いてルールとして持つ設計になっています。

CLAUDE.md——すべての起点になる「引き継ぎメモ」

Claude Codeには CLAUDE.md というファイルがあります。これはAIに対する引き継ぎメモみたいなもので、「このプロジェクトではこういうルールで動け」と書いておくと、毎回のセッションで自動的に読み込まれる仕組みです。

普通の使い方だと、チャットを開いてゼロから「こういう記事を書いて」と指示するじゃないですか。

CLAUDE.mdがあると、それが不要になります。声のトーン、禁止表現、構成ルール、過去の失敗パターン——全部ファイルに書いてあるから、AIは最初から「わどの文脈」を理解した状態で動き始める。

毎回ゼロからプロンプトを書くのと、引き継ぎメモを持ったAIに仕事を渡すのは、まったく別の体験です。

voice-guide——AIの「声」を殺して、自分の声を入れる

CLAUDE.mdと並んで重要なのが、voice-guide（声のルール）というファイルです。ここには「AIっぽさの検出トリガー」が9個定義してあります。

たとえば——

「さらに」「また」「加えて」が3回以上出たら即削除

「多くの人が〜」「〜は重要です」みたいな抽象的な一般論は全カット

「羅針盤」「旅路」「未来へはばたく」——こういう翻訳調の日本語は殺す

同じ長さの段落が3つ以上並んだら、構造を壊す

で、削除だけじゃなくて「代わりに何を入れるか」も決めてあります。

これ、一覧で見ると「当たり前じゃん」って思うかもしれない。でも実際にAIにコンテンツを書かせると、AI臭い表現のオンパレードになる。上のルールをファイルに書いておくと、AIが最初から避けてくれる。

ここがポイントで、voice-guideはプロンプトに書くんじゃなくて「ファイル」にする。プロンプトに書くと毎回コピペの手間が発生するし、書き忘れたら終わり。ファイルにしておけば、自動で読み込まれます。

143-6. 失敗談3つ——仕組みが動かなかったとき
仕組みができた今でこそ1時間で書けます。でも、最初から1時間だったわけじゃない。失敗だらけだった。

失敗1: voice-guideを読まずに書いた（これが一番痛い）

競合分析もフック設計も丁寧にやっていた。でも読み返したら、完全にAI臭かった。原因はシンプル、voice-guideを最初にReadしていなかった。

構造がよくても、声がない。「誰が書いても同じ記事」になっていた。パワーワードゼロ、エッジゼロ、失敗談ゼロ、形容詞→動詞変換ゼロ。4項目すべて0点。

この教訓を、CLAUDE.md本体のミス防止セクションに追記しました。「voice-guide未参照で記事を書くな」と。二度と同じミスをしないように。

失敗2: CLAUDE.mdを膨らませすぎた（やりがち）

voice-guideの重要性に気づいたあと、あれもこれもとCLAUDE.mdにルールを追加していった。気づいたら50行を超えていた。

結果、逆に品質が下がった。AIはルールが多すぎると、全部を均等に守ろうとして、どのルールも中途半端になる。脳内タブ地獄はAIにも起きる。

対策として、CLAUDE.md本体は「索引」に絞りました。詳細ルール（voice-guide.md / cta-library.md 等）は別ファイルに分離。AIは必要なファイルだけをその都度読み込む設計です。

失敗3: サブエージェントにvoice-guideを渡し忘れた（人間と同じ）

Claude Codeにはサブエージェント（別スレッドでタスクを並行処理するAI）がいます。メインのAIから「これやっといて」と仕事を振れる。

で、サブエージェントにnote記事の下書きを任せたら、びっくりするほどAI臭い文章が返ってきた。原因はサブエージェントにvoice-guideのパスを渡し忘れていたことだった。メインのAIは読み込み済みでも、サブエージェントは別コンテキストで動く。明示的に「このファイルを読め」と指示しないと参照してくれない。

「自分が知ってることは相手も知ってるはず」——これ、人間のチームでもある失敗じゃないですか。AIでもまったく同じことが起きる。

148-1. なぜこの7セクションで出るのか


心理フローに沿った7セクション設計

要素 目的 例 ① 権威性 信頼を作る 「累計1,000人」「250万インプ」 ② 希少性 今買わせる 「予告なく終了」「先着100部」 ③ 簡単さ ハードル下げ 「15分で設定完了」「プログラミング不要」 ④ 即効性 未来を近く感じさせる 「30日でマスター」「1時間で実感」 ⑤ 共感 自分ごと化 「AIの管理が仕事になっていた」 ⑥ 放置リスク 行動しない損失 「Chat onlyで10%しか使えていない」

Claudeに「このLPに6要素が全部入っているかチェックして」と頼むと、足りない要素を指摘してくれる。穴のないLPが短時間で仕上がります。

指摘の形はこんな感じで返ってきます。


✅ ①権威性: Hero冒頭に「250万インプ実績」あり
✅ ②希少性: Final CTAに「予告なく値上げ」あり
✅ ③簡単さ: Solutionに「10分で環境構築」あり
❌ ④即効性: 「短期間で」はあるが、具体的な日数なし
   →「30日でマスター」を追加推奨
✅ ⑤共感: Problemに「毎回初対面の徒労」あり
⚠ ⑥放置リスク: 暗示はあるが明文化不足
   →「今のままだと、Claudeの10%しか使えていない」を追加推奨
このレベルの指摘を人間のコピーライターに頼むと、1回あたり5〜10万円。Claude Codeに頼むと即日0円。しかも何度でもやり直せる。

155. やったこと — Udemyで講座を販売した
Udemy（オンライン講座プラットフォーム）に講座を出しました。

なぜUdemyか。 SNSのフォロワーがゼロでも売れるからです。Udemyはプラットフォーム自体に集客力がある。自分でSNSを育てなくても、Udemyの検索とレコメンドで受講者が来る。

これが重要なポイントです。「まずSNSを育てないと売れない」は嘘。プラットフォームの力を借りれば、コンテンツさえあれば売れます。

156. 3日間の全体像 — カリキュラム1日＋撮影編集2日＋Udemy承認
タイトルの「3日」の内訳を正直に開示します。

日程 作業 所要時間 Day 1 競合分析 + カリキュラム設計 + 台本 + スライド生成 丸1日 Day 2 全セクションの画面収録 半日〜1日 Day 3 動画編集 + Udemy入稿 半日〜1日 Day 3〜（並行） Udemyの審査・公開承認待ち 数時間〜1日

Day 3の入稿が終わった時点で、Udemy側の審査が走り、そのまま公開承認まで含めて合計3日で販売開始の流れでした。Udemy側の審査は最近は早くて、通常は24時間以内に返ってきます。

以下、日別の中身です。

156-1. Day 1: 競合分析 → カリキュラム設計 → 台本 → スライド
丸1日で、販売に必要な「文案と素材」をすべて揃えます。

まずClaude Codeに競合分析を任せました。

Udemyで[テーマ]の講座を調べて。

差別化ポイントと、自分が勝てる切り口を提案して。


Udemyで[テーマ]の講座を調べて。
上位5講座の構成・レビュー・価格・受講者数を分析して。
差別化ポイントと、自分が勝てる切り口を提案して。
リサーチ結果をもとに、カリキュラム（章立て）をClaude Codeと壁打ちしながら設計する。ここが全体の骨格になるので、1〜2時間はじっくり使います。

カリキュラムが固まったら、台本とスライドを一気にClaude Codeで生成します。

台本: 各セクションを順番に生成。voice-guideのルールが自動適用されるので、全セクションでトーンが統一される

スライド: 台本からテキスト・構成を自動生成して、パワーポイント（.pptx）まで出力。デザイナーに外注する必要がない

ここまでを1日で。以前なら「台本を手で書いて1週間、スライドをデザイナーに発注して1週間」のフローが、Claude Codeで1日に圧縮されます。

156-2. Day 2: 画面収録
台本とスライドが揃ったら、台本を読みながら画面収録するだけ。

顔出しは不要。スライド+声だけでOK。収録ソフトはMacなら標準のQuickTime、WindowsならOBSでいい。1セクション5〜10分 × 15セクションで、撮り直しを含めても半日〜1日で終わります。

156-3. Day 3: 動画編集 → Udemy入稿 → 審査
編集は「言い間違いのカット」と「音量の平準化」くらい。本格的なエフェクトは入れません。ここもソフト一任で半日。

できた動画をUdemyの入稿画面にアップロード。講座説明文・タイトル・サムネも、Claude Codeで説明文の下書きを作ってから貼り付けます。

入稿を完了すると、Udemy側で審査が始まります。動画の品質チェック・音質・著作権確認などをUdemy側がやってくれる工程で、最近は24時間以内に承認されるのが一般的。

つまりDay 3の入稿完了時点から数時間〜1日待てば、販売開始。全体で「3日で販売スタート」が実現します。

156-4. 結果
初月で15万円の売上（Udemy手数料引かれる前の表示売上ベース）。セール価格帯・受講者数はテーマ次第で上下しますが、最初の1本で5桁後半〜6桁は現実的という感触でした。

// 前月比の計算 + 異常値判定
function compareWithLastMonth(current, previous) {
  if (!previous) return { diff: null, status: "baseline" };
  const diff = (current - previous) / previous;
  let status = "normal";
  if (Math.abs(diff) >= 0.20) status = "alert";   // ±20%超で警告
  return { diff: Math.round(diff * 1000) / 10, status };
}
異常値のしきい値は±20%を目安にしています。これはわどの事業規模での経験値。業種によっては±10%でも大きな変化だったりするので、ここは自分で調整してください。

1. MCPでNotion KPIトラッカーから先月の数字を取る
2. data/kpi-YYYY-MM.json に保存

① タスクを実行する
② 結果を確認する
③ 「ここがダメだった」をrules/に追記する
④ 次のタスクではルールが自動適用される
⑤ ①に戻る
これが自己進化ループです。

次からは、ライターもリサーチャーも全エージェントがこのルールを守る。1回の修正が、チーム全体に反映される。

人間のチームなら、「全員に周知→確認→徹底」に1週間かかる。AIチームなら、ファイルに1行書くだけ。

176. 品質管理の仕組み
AIチームの最大の課題は品質のブレです。これをどう管理しているか。

176-1. レビュー → 修正 → ルール追加

ライター: 記事を書く
  ↓
品質チェック: レビュー（AIっぽさ・事実確認・一貫性）
  ↓
問題あり → ライターに修正指示
  ↓
修正後 → 再度品質チェック
  ↓
OK → 完成
  ↓
パターン化した問題 → rules/ に追加（次回から自動防止）
重要なのは最後のステップ。 同じ問題が2回起きたら、ルールに追加して3回目を防ぐ。これが自己進化ループの実装です。
